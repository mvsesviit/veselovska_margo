
# Матриця доступу — Лабораторна робота 04

## 1. Ролі та принципи

- **Reporter** — створює інциденти та переглядає лише власні.
- **Analyst** — переглядає інциденти всіх власників, включно з внутрішніми коментарями, та виконує дозволені переходи статусів.
- **Administrator** — має повний доступ до інцидентів та адміністративних операцій.
- Ідентифікатор власника визначається сервером із перевіреної автентифікованої особи. Дані власника з HTTP-запиту не вважаються довіреними.

## 2. Матриця доступу

| Дія | Reporter | Analyst | Administrator | Власник ресурсу має значення? |
|---|---|---|---|---|
| Перегляд списку інцидентів | Лише власні | Усі | Усі | Так, для Reporter |
| Перегляд деталей інциденту | Лише власні | Усі | Усі | Так, для Reporter |
| Створення інциденту | Так | Ні | Так | Власника призначає сервер |
| Зміна severity | Не реалізовано | Не реалізовано | Не реалізовано |
| Зміна status поза triage | Не реалізовано | Не реалізовано | Не реалізовано |
| Видалення інциденту | Не реалізовано | Не реалізовано | Не реалізовано |
| Перегляд звичайних коментарів | Лише в доступному інциденті | Так | Так | Так, для Reporter |
| Перегляд internal comment | Ні | Так | Так | Так, для Reporter |
| Привілейований перехід у Triaged | Ні | Так | Так | Ні для Analyst/Admin |
| Пошук інцидентів | Лише власні | Усі | Усі | Так, для Reporter |
| Зведення за severity | Лише власні | Усі | Усі | Так, для Reporter |

## 3. Політика відмови

- **401 Unauthorized** — користувач не автентифікований.
- **403 Forbidden** — користувач автентифікований, але не має необхідної ролі для операції.
- **404 Not Found** — ресурс не існує або недоступний користувачу через обмеження власника.

Для доступу Reporter до чужого інциденту використовується 404, щоб не розкривати факт існування чужого ресурсу. Відповіді для неіснуючого та недоступного інцидентів мають бути узгодженими.

## 4. Правила безпеки

1. Не довіряти `ownerUserId`, `userId`, ролям та іншим привілейованим полям із тіла запиту.
2. Ідентифікатор користувача отримувати з автентифікованого `HttpContext.User`.
3. Перевіряти доступ на сервері для кожного ресурсу, а не лише приховувати кнопки в інтерфейсі.
4. Перевіряти доступ до дочірніх ресурсів окремо, зокрема коментарів.
5. Не повертати Reporter внутрішні коментарі.
6. Не дозволяти Reporter виконувати привілейовані переходи статусів.
7. Не змінювати стан бази даних у разі відмови в доступі.
8. Аудитувати відмови без запису паролів, cookie, токенів або повного тіла запиту.

## 5. Особлива перевірка пошуку та зведень

Пошук і зведення за severity також повинні враховувати роль та власника:

- Reporter отримує результати лише для власних інцидентів.
- Analyst та Administrator можуть отримувати результати для всіх інцидентів.
- Фільтрація має виконуватися на сервері до формування відповіді.

Це усуває ризик обходу обмежень доступу через альтернативні endpoint-и.
